# 第五章 逻辑设计

## 5.1 E-R图向关系模型的转换

### 5.1.1 转换原则

将E-R图转换为关系模型遵循以下原则:

1. **实体转换**:每个实体转换为一个关系(表)
2. **属性转换**:实体的属性转换为关系的属性(列)
3. **主键转换**:实体的主键转换为关系的主键
4. **关系转换**:
   - 1:1关系:将一方的主键加入另一方作为外键
   - 1:N关系:在N端加入1端的主键作为外键
   - M:N关系:创建一个新的关系,包含双方的主键

### 5.1.2 实体关系转换

#### 5.1.2.1 用户表(users)

```sql
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '用户ID',
    username VARCHAR(50) NOT NULL UNIQUE COMMENT '用户名',
    password VARCHAR(255) NOT NULL COMMENT '密码(BCrypt加密)',
    phone_number VARCHAR(20) COMMENT '手机号',
    email VARCHAR(100) COMMENT '邮箱',
    real_name VARCHAR(50) COMMENT '真实姓名',
    status INT NOT NULL DEFAULT 1 COMMENT '状态:1-正常,0-禁用',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    INDEX idx_username (username),
    INDEX idx_phone (phone_number)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

**关系模式**:users(id, username, password, phone_number, email, real_name, status, created_at, updated_at)

**主键**:id
**唯一键**:username
**索引**:idx_username, idx_phone

#### 5.1.2.2 道路路况表(road_traffic_overall)

```sql
CREATE TABLE road_traffic_overall (
    id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '路况ID',
    request_time DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT 'API请求时间',
    road_name VARCHAR(100) NOT NULL COMMENT '道路名称',
    city VARCHAR(50) NOT NULL COMMENT '城市名称',
    api_status INT COMMENT 'API状态码',
    message VARCHAR(255) COMMENT 'API响应信息',
    description TEXT COMMENT '路况描述',
    evaluation_status INT COMMENT '拥堵等级:0-未知,1-畅通,2-缓行,3-拥堵,4-严重拥堵',
    evaluation_status_desc VARCHAR(50) COMMENT '拥堵等级描述',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    INDEX idx_road_city (road_name, city),
    INDEX idx_request_time (request_time),
    INDEX idx_evaluation_status (evaluation_status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='道路路况概览表';
```

**关系模式**:road_traffic_overall(id, request_time, road_name, city, api_status, message, description, evaluation_status, evaluation_status_desc, created_at)

**主键**:id
**索引**:idx_road_city(road_name, city), idx_request_time, idx_evaluation_status

#### 5.1.2.3 拥堵路段表(congestion_sections)

```sql
CREATE TABLE congestion_sections (
    id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '路段ID',
    overall_id BIGINT NOT NULL COMMENT '关联路况ID',
    road_name VARCHAR(100) COMMENT '道路名称',
    section_desc VARCHAR(500) COMMENT '路段描述',
    status INT COMMENT '路段状态:0-4',
    status_desc VARCHAR(50) COMMENT '路段状态描述',
    speed DECIMAL(5,2) COMMENT '平均速度(km/h)',
    congestion_distance INT COMMENT '拥堵距离(米)',
    congestion_trend VARCHAR(20) COMMENT '拥堵趋势:持平/缓解/加重',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    FOREIGN KEY (overall_id) REFERENCES road_traffic_overall(id) ON DELETE CASCADE,
    INDEX idx_overall_id (overall_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='拥堵路段表';
```

**关系模式**:congestion_sections(id, overall_id, road_name, section_desc, status, status_desc, speed, congestion_distance, congestion_trend, created_at)

**主键**:id
**外键**:overall_id → road_traffic_overall(id)
**索引**:idx_overall_id

### 5.1.3 关系模型汇总

```

```

## 5.2 数据模型的优化及规范化设计

### 5.2.1 规范化分析

#### 第一范式(1NF)验证

**定义**:关系中的每个属性都是原子的,不可再分。

**检查**:
- 所有表中的字段都是原子值
- 没有重复组
- 没有嵌套关系

**结论**:所有关系都满足第一范式。

#### 第二范式(2NF)验证

**定义**:满足1NF,且非主属性完全函数依赖于主键。

**检查**:
1. **users表**:主键id,所有非主属性完全依赖于id ✓
2. **road_traffic_overall表**:主键id,所有非主属性完全依赖于id ✓
3. **congestion_sections表**:主键id,所有非主属性完全依赖于id ✓
4. **carpool_request表**:主键id,所有非主属性完全依赖于id ✓
5. **carpool_invitation表**:主键id,所有非主属性完全依赖于id ✓
6. **trip_record表**:主键id,所有非主属性完全依赖于id ✓
7. **match_record表**:主键id,存在部分依赖问题

**match_record表的问题分析**:
```
函数依赖:
- id → request_id, user_id, trip_id, created_at (完全依赖)
- (request_id, user_id) → id, trip_id, created_at (完全依赖)
- (request_id) → (部分信息)
```

虽然match_record表存在多个候选键,但实际使用中以id作为主键,其他外键作为查询条件,因此不存在部分依赖导致的更新异常。

**结论**:所有关系都满足第二范式。

#### 第三范式(3NF)验证

**定义**:满足2NF,且非主属性不传递依赖于主键。

**检查**:
1. **users表**:不存在传递依赖 ✓
2. **road_traffic_overall表**:不存在传递依赖 ✓
3. **congestion_sections表**:通过overall_id可以获取road_name,存在轻微的传递依赖,但为了查询性能保留冗余 ✓
4. **carpool_request表**:不存在传递依赖 ✓
5. **carpool_invitation表**:不存在传递依赖 ✓
6. **trip_record表**:不存在传递依赖 ✓
7. **match_record表**:不存在传递依赖 ✓

**congestion_sections表的优化考虑**:
- 保留road_name冗余:避免每次查询都要JOIN road_traffic_overall表
- 权衡:查询性能 vs 数据冗余
- 决策:保留冗余,定期通过维护脚本保证一致性

**结论**:除个别表为了性能故意引入冗余外,所有关系都满足第三范式。

### 5.2.2 反规范化设计

在某些场景下,为了提升查询性能,有意引入数据冗余,称为反规范化。

#### 5.2.2.1 congestion_sections表的road_name冗余

**设计**:
```sql
congestion_sections (
    ...
    road_name VARCHAR(100),  -- 冗余字段
    overall_id BIGINT,
    ...
)
```

**原因**:
- 查询拥堵路段时经常需要显示道路名称
- 避免每次都JOIN road_traffic_overall表
- road_name相对稳定,更新频率低

**代价**:
- 数据冗余,存储空间略增
- 需要维护数据一致性

**维护策略**:
- 通过触发器或应用层逻辑保证同步
- 定期运行数据一致性检查脚本

#### 5.2.2.2 status_desc状态描述字段

**设计**:
```sql
carpool_request (
    ...
    status_desc VARCHAR(50),  -- "等待匹配"/"已匹配"/"已取消"
    ...
)
```

**替代方案**:
使用status INT字段,通过枚举或映射表转换为描述。

**选择原因**:
- 状态描述更直观,便于调试和日志
- 易于扩展新状态,不需要修改代码
- 查询时无需JOIN映射表

### 5.2.3 索引优化设计

#### 5.2.3.1 单列索引

**users表**:
```sql
INDEX idx_username (username)   -- 登录查询优化
INDEX idx_phone (phone_number)  -- 手机号查询优化
```

**carpool_request表**:
```sql
INDEX idx_status_desc (status_desc)  -- 按状态筛选
```

**carpool_invitation表**:
```sql

```

#### 5.2.3.2 复合索引

**road_traffic_overall表**:
```sql
INDEX idx_road_city (road_name, city)  -- 组合查询优化
INDEX idx_evaluation_status (evaluation_status)  -- 按拥堵等级统计
```

**carpool_request表**:
```sql
INDEX idx_departure_time (earliest_departure_time, latest_departure_time)  -- 时间范围查询
```

**索引设计原则**:
1. **选择性高的字段优先**:如username、phone_number
2. **频繁查询的条件**:如status、status_desc
3. **覆盖索引**:索引包含查询所需的所有字段,避免回表
4. **最左前缀原则**:复合索引按查询频率和选择性排序

#### 5.2.3.3 时间索引优化

**road_traffic_overall表**:
```sql
INDEX idx_request_time (request_time)  -- 时间范围查询
```

**用途**:
- 历史数据查询(按时间范围筛选)
- 数据归档(删除或归档过期数据)
- 定期统计(按日期/小时聚合)

**查询示例**:
```sql
-- 查询最近24小时的数据
SELECT * FROM road_traffic_overall
WHERE request_time >= DATE_SUB(NOW(), INTERVAL 24 HOUR)
ORDER BY request_time DESC;
```

### 5.2.4 分区设计考虑

随着数据量增长,可以考虑对大表进行分区。

#### road_traffic_overall表分区方案

**按时间范围分区(RANGE分区)**:
```sql
ALTER TABLE road_traffic_overall
PARTITION BY RANGE (YEAR(request_time)) (
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

**优势**:
- 查询时只扫描相关分区,提升性能
- 便于归档历史数据(直接DROP旧分区)
- 备份和恢复更灵活

**适用场景**:
- 数据量超过千万级
- 查询大多按时间范围进行
- 需要定期归档历史数据

**当前阶段**:暂不实施,数据量未达到分区阈值

### 5.2.5 视图设计

为了简化复杂查询,可以创建视图。

#### 拼车需求详情视图

```sql
CREATE VIEW v_carpool_request_detail AS
SELECT
    cr.id AS request_id,
    cr.has_car,
    cr.passenger_count,
    cr.max_passenger_count,
    cr.start_location,
    cr.end_location,
    cr.earliest_departure_time,
    cr.latest_departure_time,
    cr.status_desc,
    u.id AS user_id,
    u.username,
    u.real_name,
    u.phone_number AS user_phone,
    u.email,
    (SELECT COUNT(*) FROM carpool_invitation ci
     WHERE ci.carpool_request_id = cr.id AND ci.status = 1) AS pending_invitations,
    (SELECT COUNT(*) FROM carpool_invitation ci
     WHERE ci.carpool_request_id = cr.id AND ci.status = 2) AS accepted_invitations

JOIN users u ON cr.user_id = u.id
WHERE cr.status_desc = '等待匹配';
```

**用途**:
- 前端展示拼车需求列表
- 包含用户信息和邀请统计
- 简化应用层SQL编写

#### 交通统计视图

```sql
CREATE VIEW v_traffic_stats AS
SELECT
    city,
    evaluation_status,
    evaluation_status_desc,
    COUNT(*) AS road_count,
    AVG(speed) AS avg_speed,
    SUM(congestion_distance) AS total_congestion_distance
FROM road_traffic_overall rto
LEFT JOIN congestion_sections cs ON rto.id = cs.overall_id
WHERE rto.request_time >= DATE_SUB(NOW(), INTERVAL 1 HOUR)
GROUP BY city, evaluation_status, evaluation_status_desc;
```

**用途**:
- 首页交通统计展示
- 按城市和拥堵等级聚合
- 仅统计最近1小时的数据

### 5.2.6 触发器设计

为了保证数据一致性,可以使用触发器。

#### 更新时间自动维护触发器

虽然MySQL的`ON UPDATE CURRENT_TIMESTAMP`可以自动更新updated_at字段,但为了演示触发器用法:

```sql
CREATE TRIGGER trg_users_update_time
BEFORE UPDATE ON users
FOR EACH ROW
SET NEW.updated_at = CURRENT_TIMESTAMP;
```

#### 拥堵路段数据一致性触发器

```sql
CREATE TRIGGER trg_congestion_sections_sync_road
BEFORE INSERT ON congestion_sections
FOR EACH ROW
BEGIN
    DECLARE v_road_name VARCHAR(100);
    SELECT road_name INTO v_road_name
    FROM road_traffic_overall
    WHERE id = NEW.overall_id;

    SET NEW.road_name = COALESCE(NEW.road_name, v_road_name);
END;
```

**说明**:插入拥堵路段时,自动从关联的路况记录中获取道路名称。

### 5.2.7 存储过程设计

为了提高性能和简化应用逻辑,可以使用存储过程。

#### 拼车匹配接受存储过程

```sql
DELIMITER //

CREATE PROCEDURE sp_accept_invitation(
    IN p_invitation_id BIGINT,
    IN p_user_id BIGINT,
    OUT p_trip_id BIGINT,
    OUT p_success INT
)
BEGIN
    DECLARE v_request_id BIGINT;
    DECLARE v_request_user_id BIGINT;
    DECLARE v_inviter_id BIGINT;
    DECLARE v_passenger_count INT;
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SET p_success = 0;
    END;

    START TRANSACTION;

    -- 1. 查询邀请信息并验证
    SELECT carpool_request_id, inviter_id, passenger_count
    INTO v_request_id, v_inviter_id, v_passenger_count
    FROM carpool_invitation
    WHERE id = p_invitation_id AND status = 1;

    IF v_request_id IS NULL THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '邀请不存在或已处理';
    END IF;

    -- 2. 验证权限(只有需求发布者可以接受邀请)
    SELECT user_id INTO v_request_user_id
    FROM carpool_request
    WHERE id = v_request_id;

    IF v_request_user_id != p_user_id THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '无权处理该邀请';
    END IF;

    -- 3. 创建行程记录
    INSERT INTO trip_record (
        start_location, start_latitude, start_longitude,
        end_location, end_latitude, end_longitude,
        departure_at, arrival_at, status_desc, passenger_count
    )
    SELECT start_location, start_latitude, start_longitude,
           end_location, end_latitude, end_longitude,
           earliest_departure_time, latest_departure_time,
           '待出发', passenger_count + v_passenger_count
    FROM carpool_request
    WHERE id = v_request_id;

    SET p_trip_id = LAST_INSERT_ID();

    -- 4. 创建匹配记录(需求发布者)
    INSERT INTO match_record (request_id, user_id, trip_id)
    VALUES (v_request_id, v_request_user_id, p_trip_id);

    -- 5. 创建匹配记录(邀请者)
    INSERT INTO match_record (request_id, user_id, trip_id)
    VALUES (v_request_id, v_inviter_id, p_trip_id);

    -- 6. 更新邀请状态
    UPDATE carpool_invitation
    SET status = 2, updated_at = CURRENT_TIMESTAMP
    WHERE id = p_invitation_id;

    -- 7. 拒绝该需求的其他所有邀请
    UPDATE carpool_invitation
    SET status = 3, updated_at = CURRENT_TIMESTAMP
    WHERE carpool_request_id = v_request_id
      AND id != p_invitation_id
      AND status = 1;

    -- 8. 更新需求状态
    UPDATE carpool_request
    SET status_desc = '已匹配'
    WHERE id = v_request_id;

    COMMIT;
    SET p_success = 1;
END //

DELIMITER ;
```
