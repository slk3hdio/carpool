# 第一章 概述

## 1.1 课题背景

### 1.1.1 城市交通拥堵现状

随着我国城市化进程的加快和机动车保有量的持续增长,城市交通拥堵问题日益突出。根据高德地图、百度地图等发布的年度交通分析报告显示,在早晚高峰时段,全国主要城市的道路拥堵延时指数普遍超过1.6以上,部分城市核心区域甚至达到2.5以上。交通拥堵不仅增加了市民的通勤时间成本,加剧了能源消耗和环境污染,也严重影响了城市的运行效率和居民的生活质量。

传统的交通管理方式主要依靠道路基础设施建设、交通信号控制优化等手段,但在日益增长的交通需求面前,这些措施往往难以从根本上解决问题。因此,如何充分利用现有的道路资源,通过智能化手段提高交通系统的运行效率,成为了城市交通治理的重要课题。

### 1.1.2 智能交通系统的发展

智能交通系统(Intelligent Transportation System, ITS)是将先进的信息技术、数据通信传输技术、电子传感技术、控制技术、计算机技术和系统综合技术有效地集成运用于整个交通运输管理体系,而建立起的一种在大范围内、全方位发挥作用的,实时、准确、高效的综合交通运输管理系统。

近年来,随着物联网、大数据、云计算、人工智能等新兴技术的发展,智能交通系统迎来了快速发展的机遇。交通数据的实时采集、处理和可视化展示,为交通管理部门提供了科学决策的依据,也为公众出行提供了便利的参考信息。通过实时监测道路流量、车速、拥堵状况等指标,可以实现交通信号的动态优化、路况信息的精准推送、出行路径的智能规划等功能。

### 1.1.3 拼车模式的兴起

拼车(Carpooling)作为一种共享出行方式,通过让多个出行需求相似的用户共享同一辆私家车,可以有效减少道路上的车辆数量,提高车辆利用率,缓解交通压力,同时降低出行成本和碳排放。特别是在上下班通勤、节假日出行等场景中,拼车模式展现出了巨大的应用潜力。

传统的拼车方式主要依靠熟人介绍或线下张贴信息等方式进行匹配,存在信息传播范围有限、匹配效率低、信任度难以建立等问题。随着移动互联网技术的发展,基于互联网平台的拼车服务应运而生。这些平台通过收集用户的出行需求信息,利用智能匹配算法为用户提供拼车机会,极大地提高了拼车的便利性和可行性。

### 1.1.4 系统设计目标

本课题旨在设计并实现一个集实时交通监测与拼车服务于一体的综合系统。系统一方面通过接入第三方地图API获取实时交通数据,对城市道路的交通状况进行持续监测和可视化展示,帮助用户了解当前路况,合理规划出行路线;另一方面提供拼车信息发布、搜索、匹配、邀请等功能,促进有相似出行需求的用户之间进行拼车,提高出行效率,减少车辆空载率。

系统采用前后端分离的架构,前端使用Vue.js框架构建响应式用户界面,后端使用Spring Boot框架提供RESTful API服务,数据库采用MySQL存储系统数据。通过合理的数据库设计、系统架构设计和功能模块设计,确保系统具有良好的可扩展性、可维护性和用户体验。

## 1.3 用户需求

### 1.3.1 用户角色分析

系统主要面向以下几类用户:

1. **普通用户**:包括有车一族和无车乘客,主要需求是发布拼车信息、搜索合适的拼车机会、查看实时交通状况等。

2. **系统管理员**:负责系统的日常维护、用户管理、数据管理等操作。

3. **访客**:未注册登录的用户,可以浏览公开的交通信息,查看拼车信息,但无法发布拼车需求或进行拼车匹配。

### 1.3.2 功能性需求

#### (1) 用户管理功能

- 用户注册:新用户可以通过用户名、密码、手机号、邮箱等信息注册账号。
- 用户登录:已注册用户可以通过用户名和密码登录系统,登录成功后获取JWT令牌用于后续的身份认证。
- 个人信息管理:用户可以查看和修改个人资料,包括真实姓名、手机号、邮箱等信息。
- 密码修改:用户可以修改登录密码。
- 用户状态管理:系统管理员可以启用或禁用用户账号。

#### (2) 实时交通监测功能

- 路况查询:用户可以查询指定城市、指定道路的实时交通状况。
- 路况筛选:用户可以根据城市、拥堵等级等条件筛选交通信息。
- 路况搜索:用户可以通过关键词搜索道路名称。
- 路况统计:系统提供交通统计数据,如各拥堵等级的道路数量、占比等。
- 路况概览:在首页展示热门道路的交通状况概览信息。
- 历史数据查询:用户可以查询指定道路的历史交通数据。
- 地图可视化:在地图上标注道路位置,并通过不同颜色表示拥堵程度。

#### (3) 拼车服务功能

- 拼车需求发布:用户可以发布拼车需求,包括起点、终点、出发时间、乘客人数、是否有车等信息。
- 拼车需求搜索:用户可以根据起点、终点、出发时间等条件搜索合适的拼车需求。
- 拼车邀请:用户看到感兴趣的拼车需求后,可以向需求发布者发送邀请,说明自己的人数和备注信息。
- 邀请管理:需求发布者可以查看收到的邀请,进行接受、拒绝或取消操作。
- 行程管理:匹配成功后系统自动生成行程记录,用户可以查看行程详情和状态。

#### (4) 数据管理功能

- 交通数据采集:系统通过Python脚本定期调用百度地图API采集实时交通数据,并存储到数据库。
- 历史数据归档:系统定期对历史交通数据进行归档处理,保证系统的查询性能。

### 1.3.3 非功能性需求

#### (1) 性能需求

- 系统应能支持至少100个并发用户同时访问。
- 页面加载时间应控制在2秒以内。
- 交通数据查询响应时间应控制在1秒以内。
- 地图渲染应流畅,支持缩放、拖拽等交互操作。

#### (2) 安全性需求

- 用户密码必须经过加密存储,使用BCrypt算法进行哈希处理。
- 用户登录后使用JWT令牌进行身份认证,令牌有效期设置为7天。
- 系统应对用户输入进行验证,防止SQL注入、XSS攻击等安全漏洞。
- 采用CORS白名单机制限制跨域访问来源。

#### (3) 可用性需求

- 系统界面应简洁美观,操作流程应符合用户习惯。
- 系统应提供清晰的操作提示和错误信息反馈。
- 系统应支持主流浏览器(Chrome、Firefox、Safari、Edge等)访问。
- 系统应具有一定的容错能力,当某个功能模块出现故障时不应影响其他模块的使用。

#### (4) 可维护性需求

- 系统采用前后端分离架构,降低耦合度,便于独立开发和部署。
- 代码应遵循统一的编码规范,并添加必要的注释。
- 数据库设计应遵循规范化原则,减少数据冗余,避免数据异常。
- 系统应提供日志记录功能,便于问题排查和系统监控。

#### (5) 可扩展性需求

- 系统架构应支持水平扩展,可以通过增加服务器节点提升系统处理能力。
- 数据库设计应预留扩展字段,便于后续功能迭代。
- API接口设计应遵循RESTful规范,便于第三方系统集成。

### 1.3.4 数据需求

系统涉及的数据主要包括:

1. **用户数据**:用户名、密码(加密)、手机号、邮箱、真实姓名、状态、创建时间等。

2. **交通数据**:道路名称、城市、请求时间、API状态码、路况描述、拥堵等级、平均速度、拥堵距离、拥堵趋势等。

3. **拼车需求数据**:用户ID、是否有车、乘客人数、起点终点坐标、出发时间范围、联系电话、状态等。

4. **拼车邀请数据**:邀请者ID、拼车需求ID、乘客人数、留言、状态等。

5. **行程数据**:起点终点、坐标、出发到达时间、状态、乘客总数、匹配时间等。

6. **匹配记录数据**:需求ID、用户ID、行程ID、匹配时间等。

### 1.3.5 接口需求

系统需要提供以下接口:

1. **交通数据接口**:
   - 获取所有交通数据(分页)
   - 根据城市查询交通数据
   - 根据道路名称和城市查询交通数据
   - 根据拥堵等级查询交通数据
   - 搜索交通数据
   - 获取交通统计数据
   - 获取交通概览数据
   - 获取热门道路数据
   - 获取历史交通数据
   - 获取支持的城市列表
   - 获取指定城市的道路列表

2. **用户认证接口**:
   - 用户注册
   - 用户登录
   - 获取当前用户信息
   - 验证JWT令牌

3. **拼车服务接口**:
   - 创建拼车需求
   - 搜索拼车需求
   - 发送拼车邀请
   - 查询收到的邀请
   - 接受邀请
   - 拒绝邀请
   - 取消邀请

4. **行程管理接口**:
   - 获取行程详情
   - 根据需求ID查询行程
   - 更新行程状态

所有接口均遵循RESTful规范,使用JSON格式进行数据交换。

### 1.3.6 界面需求

系统前端界面主要包括:

1. **首页**:展示系统概况和热门道路的交通状况。

2. **交通监测页面**:以列表和地图两种方式展示实时交通数据,提供搜索、筛选、统计等功能。

3. **历史数据页面**:展示指定道路的历史交通变化趋势,支持时间范围选择。

4. **拼车页面**:展示拼车需求列表,提供发布需求和搜索需求的功能。

5. **个人中心页面**:展示个人信息、我的拼车需求、收到的邀请、我的行程等。

6. **登录/注册页面**:提供用户登录和注册功能。

所有页面应采用响应式设计,适配不同尺寸的屏幕(手机、平板、电脑等)。
